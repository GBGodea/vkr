# Фреймворк формальной верификации

## Обновление третьего семестра

Добавлен модуль `formal-verification-processor`: генерация двух точек входа JBMC по спецификациям —
проверки существования допустимых входов и проверки постусловий/инвариантов результата.
Проверяется исходный `BankArithmetic`, используемый приложением, а не копия его реализации.

Обоснование архитектуры и область применимости: [этап 2](nir-stage-2.md).
Формат спецификаций, устройство и запуск: [этап 3](nir-stage-3.md).
Описание упрощённой модели ниже относится к реализации второго семестра, сохранённой для контрольного сравнения.

## Структура проекта

Директория `vkr` теперь является Maven multi-module workspace:

- `formal-verification-core` - отдельная Java-библиотека с исполняемыми контрактами и аннотациями спецификаций.
- `bank-application` - исходный Spring Boot банковский MVP, который теперь зависит от `formal-verification-core`.

Так библиотека остается переиспользуемой для других Java/Spring-сервисов, в том числе банковских, а текущий проект показывает ее применение на конкретной предметной области.

## API библиотеки

Библиотека предоставляет:

- `Contract.requires(...)` - предусловия;
- `Contract.ensures(...)` - постусловия;
- `Contract.invariant(...)` - объектные и бизнес-инварианты;
- `Contract.assumes(...)` и `Contract.holds(...)` - проверки, удобные для verification harness;
- `ContractViolationException` с `ConditionType`, чтобы нарушение было классифицировано как precondition, postcondition, invariant, assumption или assertion;
- `ProofObligation` - представление логического обязательства `Gamma |- B` с выводом прямой формулы `Gamma -> B` и формулы для обратной проверки `Gamma & !B`;
- `BigDecimalSpec` - предикаты для денежных `BigDecimal`-значений;
- `LongArithmeticSpec` - предикаты для целочисленной модели и защиты от overflow;
- runtime-аннотации `@Verified`, `@Precondition`, `@Postcondition`, `@Invariant`.

Методы контрактов намеренно и бросают исключение при нарушении условия, и содержат Java `assert` внутри ядра. В обычном запуске это быстро выявляет сломанные предположения; в verification harness те же условия становятся явными проверяемыми утверждениями.

Пример логического обязательства для списания:

```java
ProofObligation withdraw = ProofObligation.of(
        "balanceAfter == balanceBefore - amount && balanceAfter >= 0",
        "balanceBefore >= 0",
        "amount > 0",
        "balanceBefore >= amount"
);
```

Прямая формула: `(balanceBefore >= 0) & (amount > 0) & (balanceBefore >= amount) -> (...)`.

Обратная проверка для SAT/JBMC/SMT: `(balanceBefore >= 0) & (amount > 0) & (balanceBefore >= amount) & !(...)`. Если такая формула невыполнима, постусловие доказано для всех входов из заданной области.

## Примененные банковские инварианты

В банковском приложении явно проверяются ключевые контракты:

- `Account` сохраняет непустые идентификационные поля и неотрицательный баланс.
- `createAccount` возвращает активный счет с нормализованными владельцем/валютой и неотрицательным начальным балансом.
- `deposit` требует положительную сумму и гарантирует увеличение баланса ровно на эту сумму.
- `withdraw` требует положительную сумму и достаточность средств, а затем гарантирует уменьшение баланса ровно на эту сумму без ухода в минус.
- `transfer` требует два разных активных счета одной валюты и достаточность средств на источнике; затем гарантирует уменьшение источника, увеличение получателя и сохранение общей суммы.
- `blockAccount` гарантирует заблокированное состояние и заполненные метаданные блокировки.

Ошибки пользовательского ввода по-прежнему возвращаются через `BankException`. `ContractViolationException` означает внутреннее нарушение спецификации: код или состояние нарушили условие, которое после нормальной валидации должно быть невозможным.

## JBMC harness

Направлять JBMC сразу на полный Spring-сервис невыгодно: репозитории, часы, UUID, `BigDecimal` и состояние фреймворка резко увеличивают пространство поиска. Для bounded verification добавлена упрощенная модель:

- `bank-application/src/test/java/com/example/bank/verification/VerifiedAccountModel.java`
- `bank-application/src/test/java/com/example/bank/verification/BankOperationVerificationHarness.java`

В harness деньги представлены как `long` в копейках. Символьный ввод задается через `org.cprover.CProver.nondetLong()`, а `CProver.assume(...)` ограничивает входы областью, где метод обязан работать:

- балансы неотрицательны;
- сумма операции положительна;
- сумма списания или перевода не превышает баланс источника;
- сложение не переполняет `long`.

После этого harness вызывает `deposit`, `withdraw` и `transferTo` и проверяет Java `assert`-постусловия.

Это соответствует обратному методу из пособия: JBMC ищет интерпретацию, где все `assume`-гипотезы истинны, но хотя бы один `assert` ложен. Если контрпример не найден в заданных границах, то для этой модели не найдено состояние, нарушающее постусловие.

Запуск:

```powershell
mvn test
.\scripts\run-jbmc.ps1
```

Ручная команда JBMC после `mvn test-compile`:

```powershell
jbmc --classpath "bank-application\target\test-classes;bank-application\target\classes;formal-verification-core\target\classes" com.example.bank.verification.BankOperationVerificationHarness
```

## Пример JML-контракта

Самый показательный метод - упрощенный перевод:

```java
void transferTo(VerifiedAccountModel target, long amountCents)
```

JML-контракт находится в `VerifiedAccountModel.java` и задает:

- существование целевого счета;
- активность обоих счетов;
- совпадение валют;
- положительную сумму;
- достаточность средств на источнике;
- отсутствие переполнения баланса получателя и общей суммы;
- область изменения только двух балансов;
- уменьшение источника на сумму;
- увеличение получателя на сумму;
- сохранение общей суммы;
- неотрицательность обоих балансов после перевода.

Этот контракт строже обычных тестов, потому что описывает всю допустимую область входных данных, а не несколько примеров.
